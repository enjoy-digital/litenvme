# Introduction {#introduction}

This chapter says what LiteNVMe is, what it does and what it does not do, and how far each part
has been tested. It ends with the layout of the repository and a map of the manual. Every reader
should start here.

## What the project is {#intro-what}

LiteNVMe lets FPGA logic store data on an off-the-shelf NVMe SSD. The FPGA is the PCI Express root
port, so no computer and no operating system sit between the logic and the drive. The core brings
the SSD up, creates its queues, then reads and writes sectors on behalf of the logic.

In NVMe terms, the FPGA is the *host*. It owns the memory where the commands, the completions
and the data live, and the SSD reads and writes that memory itself. The figure below shows the
parts of a LiteNVMe design.

![LiteNVMe at a glance. The LitePCIe root port carries the PCI Express link to the SSD. The core
reaches the SSD registers through its accessors, serves the SSD's memory requests from its
host-memory window, and runs the I/O commands in its I/O engine. A soft CPU or the RTL init
sequencer brings the SSD up; user logic then moves blocks.](intro_overview.svg)

The core is a set of Migen and LiteX modules on top of a LitePCIe root port. It is used as a
LiteX library in a LiteX SoC, or as a standalone Verilog core generated by `litenvme_gen` from a
YAML configuration (see [Integration](#integration)).

The reference bench is an Alibaba XCKU3P card, a Kintex UltraScale+ board, with the SSD on a
PCIe-slot-to-M.2 adapter. The photo below shows it.

![The reference bench: an Alibaba XCKU3P card plugged into the PCIe-slot-to-M.2 adapter that
carries the SSD.](litenvme_setup.jpg){width=75%}

## Why LiteNVMe {#intro-why}

An NVMe SSD is the cheapest way to give an FPGA design gigabytes per second of storage. A
computer normally drives it through an operating system driver; an FPGA design that records or
replays data would then need a computer in its data path.

LiteNVMe removes that computer. The FPGA plays the root complex: it enumerates the SSD,
programs it and keeps many commands in flight from hardware, without a CPU in the steady-state
loop. The [NVMe primer](#nvme-primer) explains what this involves.

The core is small and open. Every block can be simulated with the Python models of the test
suite, observed with LiteScope on the bench and changed, and the same Python describes both the
LiteX library and the generated Verilog core.

## Features at a glance {#intro-features}

| Area | Features |
|--------------------|------------------------------------------------------------------------|
| PCI Express | LitePCIe root port; configuration accessor (CfgRd0, CfgWr0), BAR0 MMIO accessor, doorbell accessor, root port configuration through the hard IP cfg_mgmt port |
| Host memory | Host-memory window that serves the SSD's reads and writes: BRAM backend, PCIe-side responder, AXI arbiter for the core's own masters, hook for an external AXI backend |
| I/O | Hardware I/O engine on one I/O queue: SQE build, PRP1, PRP2 and PRP lists, doorbell coalescing, CQE reaping by phase bit, up to `qd` commands in flight |
| Front-ends | Block streamer (AXI-Stream sectors in and out through a staging region), request generator (sequential requests for benchmarks), or the raw request and completion streams |
| Bring-up | Firmware on a soft CPU (`bench/firmware`), or the RTL init sequencer for a CPU-less design |
| Integration | `LiteNVMe` class for LiteX SoCs; standalone Verilog core from `litenvme_gen` (UltraScale+ PHY) |
| Bench | Alibaba XCKU3P target, firmware console, Etherbone host tools, harness scripts, LiteScope probes |
| Verification | Python models and 46 pytest cases from the accessors to the engine, the front-ends, the init sequencer and the generator configuration |

| External host-memory backend (LiteDRAM) | In development | Code hook, never run |

The status words mean:

- **Validated on hardware**: in normal use on a board, with the board's own output recorded in
  the repository. Numbers are given only where such a record exists.
- **In development**: not yet in normal use, or with no recorded run on a board. The evidence
  column says what exists: a document of the repository, a unit test or a build.

The Gen3 logs print the link status (`link_status=0x20ad`, Gen3 x4) and come from the harness
of the only bench target, but do not name the bitstream. The Gen2 engine logs name the bench
bitstream (`alibaba_xcku3p.bit`) and print `LINK=0x209d` (Gen2 x4); the 128-bit width of that
design is stated in `doc/NVME_PERFORMANCE.md` only.

The queue-depth sweep records neither the board nor the link: only `doc/NVME_PERFORMANCE.md` places
it on the Gen2 x4 design.

The 7-Series run is described by a commit message only, which names neither the board nor the SSD;
it is the origin of the completion byte count of the host-memory window ([The host-memory
window](#host-memory)). The recorded throughputs, with their board, SSD and settings, are in
[Performance](#performance).

## Known issues {#intro-issues}

The code of the default branch has the defects below. They are described here once, as the code
is today; the chapters link to this table. Each is a candidate for a fix in the code, after which
the manual follows the code.

| Issue | Effect |
|----------------------|----------------------------------------------------------------|
| Firmware linker scripts | `bench/firmware/linker.ld` and `linker_rom.ld` lack the `.preinit_array` and `.init_array` sections that the startup code of current LiteX walks: the firmware does not link (`undefined reference to '__init_array_start'`). The bench target ignores the status of `make`, so it still builds a bitstream, without `firmware/firmware.bin`. See [Getting started](#gs-build). |
| PHY register names | Current LitePCIe names the registers of the PHY `pcie_phy_*` (`pcie_phy_link_status`). The firmware (`status` prints `pcie_link: (no CSR)`), `hw_link_decode` of `bench/hw_common.sh` and the bench PC scripts use `pcie_phy_phy_*`, and the scripts stop with an error. The recorded logs predate the rename. See [Getting started](#gs-load). |
| `--no-compile` of the bench target | `--build --no-compile` still runs Vivado: the bench SoC cannot be elaborated without vendor tools from the command line. See [Bench SoC](#ex-soc). |
| Duplicate register banks | `add_csrs()` registers the blocks of a `LiteNVMe` again, next to the bank that LiteX collects from the attribute; the generator calls it, so a generated core has each register twice. See [Registers](#arch-registers). |
| Generator firmware modes | The firmware uses the register names of the bench SoC. With `firmware: auto` or `minimal` its compilation fails and the generator stops; with `firmware: none` no firmware initializes the generated core. See [Bring-up modes](#integ-modes). |
| Root window of the init sequencer | The sequencer writes the window value at cfg_mgmt dword `0x20` (byte `0x80`, inside the PCI Express capability of the root port) instead of dword `0x08` (Memory Base and Limit, byte `0x20`): the memory window of the root port is not programmed. No hardware log shows the effect. See [Init sequencer](#boot-rtl). |
| Read completions not split | The window answers a MemRd with one CplD of `len` dwords, whatever the MPS of the link. Neither bring-up path programs the MRRS of the SSD (512 bytes at reset), so with the init sequencer (MPS 128 bytes) a read above 128 bytes gets an oversized completion. Confirmed in simulation; the bench SSD runs at MPS 512 with the firmware. See [The responder](#mem-responder). |
| Firmware CQE read order | The firmware reads CQE dwords 0 to 2 before dword 3, which holds the phase bit, so SQ head and SQ ID may be read before the SSD wrote them (`SQ ID : 0` in `nvme_init.log`). See [Firmware](#ex-firmware). |
| `nvme_write` pattern | `nvme_write` fills 4 KiB of its buffer with `0xa5a5a5a5` and ignores the pattern of `nvme_fill`; `nvme_verify` is not affected. See [Data integrity](#ex-integrity). |
| `qd_sweep.py` | Sends the `nvme_bench` command, which the firmware no longer has. See [Bench PC tools](#ex-host). |
| Generator data width | `data_width: 512` passes the checks of the generator, then the window refuses it at elaboration. See [Build options](#opt-gen). |
| False path with `clk_external` | The generator declares no false path between an external `sys` clock and the PCIe user clock, which the root configuration accessor relies on. See [Ports](#integ-ports). |
| PERST# timer of the generator | The timer runs in `sys`, whose reset is the user reset of the hard IP, and it drives the reset of the hard IP: if the hard IP holds its user reset while its own reset is asserted, PERST# is never released. Seen in a model of this loop, not on hardware. See [PERST#](#boot-perst). |
| Lost completion | A timeout frees the accessor but not the TLP controller of the crossbar: the later reads of the three master ports wait behind the lost one and time out too, until the core is reset. See [The shared accessor](#acc-shared). |
| `csr_we` description | The window debug register `csr_we` is described as a pulse in the gateware; it is a level, and the write repeats while it stays at 1. See [Register debug port](#mem-debug). |
| Repository notes | `bench/NOTES.md` and `bench/firmware/README.md` describe commands that the firmware no longer has; `README.md` and the notes of `doc/` quote throughputs that no log records. This manual uses the code and the logs only. See [Performance](#performance). |

## What it is not {#intro-limits}

LiteNVMe is a compact host for one SSD. It leaves out the parts of NVMe that a recording or
replay design does not need:

- No interrupts. The core and the firmware poll the phase bit of the completions; MSI, MSI-X and
  INTx are not used.
- One I/O queue. Bring-up creates one submission queue and one completion queue, both number 1,
  and the I/O engine drives them.
- Read and Write only. No Flush, no Dataset Management and no other I/O command; the admin
  commands are those of bring-up.
- 512-byte sectors only. The core does not read the namespace format; the namespace number is
  given with each request.
- PRP only, no SGL. A data buffer is contiguous and starts on a 4 KiB boundary of the
  host-memory window.
- No file system: the core reads and writes raw sectors.
- The host-memory window is FPGA block RAM on hardware. A window in external DRAM is a hook of
  the code, not a tested configuration.
- The generator supports the UltraScale+ PHY only (`USPPCIEPHY`). No Gen4 or faster link has
  been run.

## Repository layout {#intro-layout}

| Path | Content |
|-----------------------------------|----------------------------------------------------------|
| `litenvme/core.py` | The `LiteNVMe` class: the core assembled on a root port |

| `bench/firmware/` | Bring-up and benchmark firmware of the soft CPU |
| `examples/` | Configuration file of the generator |
| `test/` | Unit and simulation tests (pytest) and their models |
| `doc/` | This manual (`doc/manual/`), its figures (`doc/diagrams/`), images and design notes |
